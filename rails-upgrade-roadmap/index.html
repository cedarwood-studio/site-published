Rails Upgrade Roadmap · $2,500 fixed

A checked test run of your Rails upgrade, before you commit to it.

A first pass at a Rails upgrade is cheap now. What costs you is what that pass misses. On our public sample, the first automated run found four of the eight lines flagged as breaking, and shipped a stage that passed every check and didn't start with one feature switched on. This service is the checking that came out of that. For a fixed $2,500 we test-run the first version step of your upgrade in a sandbox, start the app under each of its configurations, read the code your tests never run, and put the result through a separate review. You get a report of what broke, with the file and line and numbers a script confirms, and a staged plan. We call the report an Upgrade Roadmap.

Covers: Rails apps on 7.0 or later, going no further than 8.1, whose test suite runs without production secrets and needs no service beyond MariaDB and Redis. Earlier Rails versions, suites that need PostgreSQL, a private gem source or a browser, and other frameworks aren't offered yet. Node.js upgrade runs are next, though the sandbox doesn't yet install a Node.js app's dependencies or run its test suite or package resolver. If yours doesn't fit, the checks themselves are listed on this page.

B

What we run

It needs read-only access to the repository, with the lock file committed. We don't touch production, and we don't push to your repository or change anything in it.

  • The dependency resolver, at every version step. We run Bundler for real at each step of the path, with its most careful update. You see which gems block a step, which ones it had to downgrade and which ones the step drops, and you get the lock file for each step.
  • Your test suite, in a clean container. What passes with the network off, how long it takes, the deprecation warnings it prints today, and which lines it executes.
  • Your app, started under each configuration. We start it once for each optional feature it has, before any change, so a later step can be held to "still starts."
  • The first version step, attempted. We move Rails one release series in the sandbox, run the suite and start the app again under each configuration, and report the tests that fail and the processes that don't start. It's a trial, and it isn't a finished or reviewed stage. If a gem blocks the step, the report says which one and what unblocks it.
  • A search of your code against the documented changes. We search your code for the breaking changes in the Rails release notes and component changelogs for your path. Each match names the file and line and links the upstream source, and we read it against the line.
  • The code your tests never run. We list the framework calls the suite loads and never executes, and read them against the changelogs. We search your code for the gems a step drops.
  • Upgrade work you already have. We read your own branches and open pull requests for this upgrade first, and say what they cover and what they miss.

Before you get the report, a review pass that had no part in writing it goes through it with a fixed method, and what it added or corrected is marked. Then a person reviews it before delivery.

How you can check it. Each finding cites a file, a rule or a measurement, and a script confirms each number against the measurement it came from. Your own engineers can go through it line by line.

C

What the run can't tell you

  • That it found everything. On one stage of the sample, each later review round still found something, smaller than the round before.
  • What the later steps break when run. The first version step is attempted. The later ones are resolved and searched, and they aren't run until the upgrade itself. A trial also misses things. On the sample, the first build of the 7.2 step passed every test and still didn't start with one feature on, and it was the start-up check that showed it.
  • That behavior stays the same. Frameworks change behavior on purpose. On the sample, the step to Rails 7.2 changed how one time zone maps, the headers on some error responses and the format of the Rails log. Each was declared with its source.
  • A narrow estimate. The report carries an effort range built from your code. On the sample it's 30 to 263 hours for ten stages, and no finished upgrade has corrected the numbers behind it yet. The figure to budget from is our quote.
  • Anything only production shows. Production configuration, data volumes and traffic aren't in the run. Neither is a breaking change that no changelog lists. Code your tests never load is read and never run.
  • How it goes on a harder app. The method has run on one app, with one blocked gem and a fast test suite. An app with a dozen blocked gems and thin tests would produce a very different report.
D

If you go ahead with the upgrade

The upgrade is quoted individually from your report, in writing, before any upgrade work starts. The $2,500 comes off it. Neither of us is obliged to go on to the upgrade.

On the sample it ran one stage per pull request. F

What it covers today

Offered
Ruby on Rails upgrades that start at 7.0 or later and end at 8.1 or earlier, for apps with a test suite that runs without production secrets and needs no service beyond MariaDB and Redis.
Shown so far
One public repository, with an RSpec suite on MariaDB. There the first version step ran as a separate stage after the report, and running it as a trial inside the report is new. Redis, Minitest and private repositories are supported and haven't been run on a sample yet.
Not yet offered
Upgrades that start before Rails 7.0, since our rules cover the changes in 7.1, 7.2, 8.0 and 8.1. Apps whose tests need PostgreSQL, a private gem source, private git dependencies or a browser, which the sandbox doesn't run yet.
Not offered
Node.js, Python, Django, PHP and Laravel upgrades, and base image or database upgrades. The method hasn't been run end to end on any of them.
Out of scope
Apps with no tests, and desktop and mobile apps.
