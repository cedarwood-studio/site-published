A

What the report measures

It's for a team that waits on CI every day. Builds that used to take five minutes now take twenty, and a failed run gets retried before anyone reads the log.

  • Run time and runner minutes. The median over the last 30 days of runs on your main branch and pull requests, or the last 100 runs if those reach back further, and where the time goes by job and by step.
  • Failure rate and re-run rate, and which jobs and steps fail. The report states the window each rate was measured over, and says when that window is too short to judge a rare failure.
  • Jobs that failed and then passed on the same commit. For pytest and unittest the report names the tests the job log names, ranks them, quotes the error line and links the log. It doesn't say why a test is flaky. The names come from job logs, which GitHub keeps for 90 days by default, and some failures name no test, like a step that ran past its time limit.
  • Third-party actions that aren't pinned to a fixed version, are archived, or run on a runtime GitHub has deprecated.
  • Dependency caches that are missing or aren't being hit. We read the hit rate from job logs.
  • The changes, ranked by what they save, each with its size.

Where the top change is a speed fix that can be tested on a fork, we test that one change there and show the runs before and after. For a private repository that takes a fork you give us access to. It's optional, and you get the full report without it. We don't need write access to your own repository.

How you can check it. The report prints the query behind each number, and the data it ran on comes with it.

An engineer with the GitHub CLI could pull most of these numbers in an afternoon. What the $500 buys is that afternoon, each rate with the window it was measured over, a named person answering for the report and, where the top change is a speed fix that can be tested on a fork, that fix shown by runs before and after.

B

What it doesn't cover

  • Why a test is flaky, or a fix for it. The report names the test and shows the evidence. Finding the cause is separate work, and we don't sell it today.
  • Your application code. It reads CI history and workflow files. It isn't a security audit, a code review or an assessment of test quality.
  • A guaranteed finding. A well-kept pipeline may have little to change, and then the report says so.
  • Anything the history doesn't hold. Each report has a section on what couldn't be measured from the data and why.
