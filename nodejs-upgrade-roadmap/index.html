What's in the report

  • The breaking changes in your code. Each one names the file and line, the version step and the upstream change behind it.
  • What your tests can't catch. The code your suite never runs is checked against the same changes, and the report says whether your app still starts.
  • The dependencies in your way. For every step on the path, the packages that won't install or run on it, found for every step on the path.
  • The libraries around the runtime. Where your app uses Express, Jest, Vitest, Mocha or TypeScript, the major version changes on the path and where they hit your code.
  • The first version step, attempted. We move your app one Node.js step in the sandbox and report the tests that fail and the processes that don't start. If a package blocks the step, the report says which one and the plan stage that replaces it. The later steps are assessed in the report, and they run when the upgrade does.
  • A staged plan. Each stage says what it changes, what blocks it and what it should take, with the effort range and what drives it.
  • The evidence. Each finding cites the file, the upstream source or the measurement behind it, and a script checks the report's numbers against the data they came from. Your engineers can go through it line by line. It comes as files: the report, the plan and the data behind them.

Every report is carefully reviewed before it's delivered.

Out of scope: doing the upgrade itself, which is quoted separately, and anything in production. The report is assessed from a read-only copy of your repository in a sandbox.

C

Why reading the release notes isn't enough

Changing the version and fixing what the tests complain about is the easy part, and the install can fail before a single test runs. This is what we found running the upgrade on the example below, an open-source Node.js development server.

  • The committed lock file stopped installing at Node.js 20, because a native package, node-sass, no longer builds there. Every later step failed the same way until it was replaced.
  • The step to Node.js 18 broke four tests that passed on 16. localhost began resolving to the IPv6 address first. A read-through of the changes had listed it as a difference to accept, and running the step showed it was a failure.
  • Node.js 20 rejects HTTP/1.1 requests that have no Host header, which changed two of the app's recorded responses. A separate review added that check to the report.
  • A start-up option made the server exit at launch on every version. The report flagged it before any upgrade work began.

The report is built to find these before you commit. The plan breaks the upgrade into small stages, each with its own check.
