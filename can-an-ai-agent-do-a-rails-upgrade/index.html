Measured answer

Can an AI agent do a Rails upgrade?

On the one app we measured, an automated pass did most of the edits, and fast. Left alone, it missed half of what was flagged as breaking. The first pass on a 27,000-line Rails app found four of eight flagged lines and shipped a stage that passed every check and didn't start with one feature switched on.

Last updated November 17, 2026

A

What the first pass did

The app is Postal, an open-source mail server on Rails 7.1.6, with 851 test examples. Nobody at the Postal project asked for this, and we aren't affiliated with the project. The target was Rails 8.1. The first run was our own automated pipeline as it stood then: a search of the code against rules taken from the release notes, then a staged build, with no review.

The first run took 16.1 minutes of machine time to produce a report, with no review. Its search found four lines that documented Rails changes would break. Three stages then went onto a fork, and each passed every check we had: the test suite, a comparison of 170 recorded HTTP responses, and the same checks again on GitHub Actions.

Then the work got a review, by a separate automated pass that had no part in producing it. It read the Rails component changelogs and compared our branches with the Postal project's own upgrade work. It found four more breaking lines, and one of them was already a defect in the third stage. With an optional start-up feature switched on, the app didn't start on Rails 7.2. The test suite loads that line and never executes it, so no check we had could see it.

B

What we changed

  • An independent review is a fixed step. Every report and every stage gets a review pass that had no part in writing it. It reads the changelogs for the version step, reads every framework call the suite never runs, compares with any upgrade work the project already has, and tries to break the stage. A stage isn't published until a review passes it.
  • The rules got wider. They now come from the component changelogs as well as the release notes. Every gem a step drops from the lock is searched for in the app. Framework calls the suite loads and never runs are listed and read. The app is started once per optional feature, before the upgrade and after every stage.
  • Baselines are generated from the runs. The first report's sentence about the test suite claimed more than its runs showed. The sentence is now built from the results, and a checker rejects a report that claims more. On the sample it reads "834 of 851 examples pass with the network off; 17 more pass with the network on; 5 fail in that run."

We ran the new review on the defective stage as it stood, without telling it what had been found. It found the defect in 6.7 minutes by starting the app with the feature on, and found two more problems with the stage.

One caution about the second run's eight of eight. Four of those lines are found by rules we wrote after the first review named them. That shows the rules work on a known answer. It doesn't show the search would find them cold. The first review also had the project's own upgrade branches to compare against, which most apps won't have.

C

What it means if you try it

Our first run produced a plan that read well and made most of the edits. It took 16 minutes and it was half right. Three of the four misses were in code that no test runs. A current coding agent that loops on running, starting and fixing may do better than that first run did. We haven't run one on the same commit to compare.

If you run an agent on your own upgrade, these are the checks that caught what ours missed.

  1. Start the app the way production starts it, once for each optional feature, before the upgrade and after every step. A green test suite didn't show a process that wouldn't boot.
  2. Read the component changelogs for each version step, and don't stop at the release notes. We found the password reset break only through the Active Model changelog.
  3. Diff the lock file at each step and search your code for every gem that left it. Two gems left ours while the app still used them.
  4. List the framework calls your tests load and never execute, and read each one against the changelogs. The line that broke start-up was on that list.
  5. Update the lock conservatively. An unconstrained update on our 7.2 step moved 26 gems the step didn't need.
  6. Have something that didn't write the change review it, and have it measure what it claims. One of our own review findings was wrong, and a later review caught it by running the code.

What we can't tell you is how this goes on a harder app, or what a senior Rails engineer's read would add. The sample is one easy app, four of its ten stages have run, and no person has reviewed it yet.
