B

What's in the report

  • The breaking changes in your code. Each one names the file and line, the version step and the upstream change behind it. We read each match against your code before it's counted.
  • What your tests can't catch. The code your suite never runs is checked against the same changes, and your app is started under each of its configurations.
  • The dependencies in your way. For every step on the path, the gems that block it, the ones that change underneath you and the ones the step drops.
  • The first version step, attempted. We move your app one release series in the sandbox and report the tests that fail and the processes that don't start. If a gem blocks the step, the report says which one and what unblocks it. The later steps are assessed in the report, and they run when the upgrade does.
  • A staged plan. Each stage says what it changes, what blocks it and what it should take, with the effort range and what drives it.
  • Upgrade work you already have. If there's a branch or an abandoned attempt, the report says what it covers and what it misses.
  • The evidence. Each finding cites the file, the upstream source or the measurement behind it, and a script checks the report's numbers against the data they came from. Your engineers can go through it line by line. It comes as files: the report in Markdown and as one HTML page, the plan as JSON, the data and the check script.

Before the report reaches you it gets a separate review pass, and then a person's review.

In scope: a Rails upgrade from 7.0 or later to 8.1 or earlier, assessed from a read-only copy of your repository in a sandbox. Out of scope: doing the upgrade itself, which is quoted separately, and anything in production.

C

Why a first pass isn't enough

Bumping the version and fixing what the tests complain about is the easy part. What it leaves behind can reach production. This is what happened on our public sample, a 27,000-line app with 851 tests.

  • An automated first pass found four of the eight lines flagged as breaking. The other four only turned up in a separate review.
  • One stage passed the full test suite and a comparison of 170 recorded responses, and the app still didn't start with one feature switched on. The tests load that line and never run it.
  • The step to Rails 7.2 changed behavior without failing a test. One time zone moved by an hour, and some error responses changed their headers.

The report is built to find the first two kinds before you commit. The third is why the plan ships in small stages, each with its own check.
