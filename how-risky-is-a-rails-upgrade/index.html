Measured answer

How risky is a Rails upgrade, and how can you tell before you start?

We took Postal, an open-source Rails app of about 27,000 lines, from Rails 7.1 to 8.0 in stages and recorded what broke. Measured on the unchanged code, the numbers pointed at the risk. Of the 16 lines in the app's code that we confirmed by reading to match a documented breaking change, the test suite ran 4. A first pass found four of the eight lines flagged as breaking. A separate review pass found the other four, and one of them had already shipped in a stage that passed every test and wouldn't start with one feature switched on.

Last updated November 18, 2026

A

Where the app started

Postal is an open-source mail server, MIT licensed, with 851 test examples. At the commit we measured it pins Rails 7.1.6, a series that had been past end of life for more than a year, and the nearest series still getting security fixes was 8.1, three steps away. We aren't affiliated with the Postal project.

These numbers describe the unchanged code, the commit the upgrade started from. We took them in our second run on that commit, after the first attempt described below had shown what to look for.

The first two rows made it look easy. One blocking gem, a development tool, and a fast suite put this app at the easy end. The suite was strong on the library code and thin on the web interface, the background worker and anything behind a setting, and the three breaks we ranked highest all sat in lines it doesn't run. A green test run said very little about this upgrade, as the first attempt showed.

B

How we staged it

The plan has ten stages. We carried out the first four on our own fork, each as its own pull request. The record of each stage is public.

  1. 65 new tests that pin down how the app behaves today, before any version moves.
  2. The blocking gem removed.
  3. Rails 7.1.6 to 7.2.4.
  4. Rails 7.2.4 to 8.0.5.2.

Each stage has to keep the same behavior on the new version. The tests that passed before still pass, and 170 recorded HTTP responses come back the same or each difference is written down with its upstream source. After the first attempt we added two more conditions: the app still starts in every configuration it started in before, and the lock file moves only what the step needs.

C

The break every test missed

A first pass through the upgrade found four of the eight lines flagged as breaking on the way to 8.1. One of its four, a change to column order in schema.rb, was later read as not a break at this target, because Rails 8.1.4 reverted it. In that first run, three stages went onto the fork, and each passed the test suite, the 170 recorded responses and the same checks again on GitHub Actions.

Then a separate review pass on that first run, which also compared it with the Postal project's own upgrade branches, found the other four. Where an app has an upgrade branch or an abandoned attempt of its own, the report reads it. One of the four was already in the 7.2 stage. Rails 7.2 moved migration_context from the database connection to the connection pool, and Postal calls it in the code that waits for migrations at start-up. With that feature switched on, the app exits with a NoMethodError before it serves anything. The test suite loads that file and never runs the line, so every check was green.

The other three wouldn't have shown up in the stages that ran.

  • On 8.0, has_secure_password defines its own password_reset_token, which hides the app's database column of the same name, so every reset link lands on "This link has expired" and no test fails. The fix is one option, reset_token: false. We later wrote 6 tests that walk a reset, and on 8.0 4 of them fail without the fix.
  • On 8.1, Active Support stops depending on the benchmark gem, so it leaves the lock file, and the mail worker calls Benchmark without requiring it. No test loads that file. By our reading the worker would log the error and keep running, with the job never started, so mail would likely stop moving while the process looked healthy.
  • On 7.1 and 8.0, by our reading of the source, version 3 of the json gem rejects an option Active Support passes. Nothing pins the gem, so nothing fails until an unrelated update moves it, and then every to_json call does.

The full list of breaks, with each file and line, is on the page about what the upgrade broke.

D

What the stage reviews found

We then ran the work again on the same commit and put the 7.2 stage, as first shipped, through the same review pass, blind to what had been found. Starting the app with the feature on hit the crash. The lock file had also moved 26 gems the step didn't need, mail, nokogiri and rack among them, which loaded a different version of the YAML library in an app that stores two columns as YAML.

The stage went back four times and was reviewed five times before a review passed it. Each round found something the round before hadn't.

  • In production, a HEAD request that ends in an error page gets Content-Length: 0 on 7.2 where 7.1 sent the page's length. No recorded request could show it, because none of them is a HEAD request.
  • The line Rails logs for each request ends differently on 7.2. No changelog mentions it. Comparing the two installed versions turned it up.
  • One catch was against our own plan. The plan said this step would change where the app takes its secret key from in development and test. Measuring it on both versions showed nothing changes, and the claim came out.

On 7.2 the "Astana" time zone maps to a different zone, so a user who stored it sees times an hour off, and 5 of the 170 responses changed with it. No test failed. The 8.0 stage passed its first review, with three more differences to write down.

E

What a browser showed

We also compared the running app in a browser on Rails 7.1.6 and on the 8.0 stage, 118 screen states at a desktop and a phone width, both in the test environment. No screen broke, and the browser agreed with the tests and the recorded responses. The what-broke page has the numbers and two of the images.

F

What it means for your upgrade

On this app the risk sat where the tests didn't reach. Before you start, the number we'd look at first is how much of what the upgrade touches your suite actually runs. Here it was 4 of the 16 confirmed lines outside the lock file, and in hindsight that said more than the suite's line coverage, 83.7 percent of the lines in the files it loads, or the count of deprecation warnings, which was zero.

The second lesson is that one pass wasn't enough. That's why our work gets a separate review before it moves on.

Whoever does your upgrade, these are the questions we'd ask of the result.

  • Does the app start in every configuration production uses, after every step? A green suite didn't show a process that wouldn't boot.
  • What checked the code no test runs? That's where the worst breaks were.
  • What changed in behavior without failing anything, and is each change written down with its source?
  • Did the lock file move only what the step needed?
  • Was the work reviewed independently of whoever did it, and did that review run the app or only read the diff?

This is one app, at the easy end, and four of its ten stages. The stages still to run, Rails 8.1 and the framework defaults, are the ones that touch cookies, sessions and how stored data is serialized.
